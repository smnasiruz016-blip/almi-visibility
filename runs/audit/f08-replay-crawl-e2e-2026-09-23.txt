2 · THE MEASUREMENTS THE THIRD PROFILE STANDS ON
────────────────────────────────────────────────────────────────
- External tool: `gh run download <run> -n <artifact> -D <dir>` — fills the directory it is given. Preparation is
  therefore OBSERVABLE if it is given a staging directory instead of the live one.
- Directory rename on the owner's host (win32, Node v24.15.0), probe run 23 Sep:
      rename(dir -> existing NON-EMPTY dir)  THROWS EPERM
      rename(dir -> existing EMPTY dir)      THROWS EPERM
      rename(dir -> ABSENT path)             succeeds
  So a whole-directory replace is TWO atomic renames (live aside, staged in), not one. POSIX was not measured here and
  nothing depends on it.
- fsync law: none in this repository (unchanged). COMMITTED means the renames returned and the target re-read.
- Recovery law: none (unchanged). A discovered state is discarded or re-prepared by its named owner, never repaired.

3 · THE PROFILE — STAGED_DIRECTORY_REPLACE (src/governance/governed-write.mjs, durability-adapters.mjs)
────────────────────────────────────────────────────────────────
RETURNED   REFUSED · COMMITTED · FAILED_BEFORE_COMMIT · RECOVERY_REQUIRED                              (4)
DISCOVERED PREPARED (abandoned staging) · RETIRED (abandoned live copy) · TARGET_ABSENT — each owned by
           NEXT_GOVERNED_WRITE_TO_SAME_TARGET, which discards its own by name and re-prepares       (3)
UNREACHABLE ALREADY_COMMITTED — the intended bytes do not exist until the tool runs, and the boundary must
           inspect before any attempt is recorded                                                     (1)
           8 accounted, remainder 0. Kept apart from the owner ruling's 9 · 2 · 1 = 12 (RULED_PROFILES).

Stage by stage — what is left if it stops there:
  before ATTEMPTED          nothing changed
  populate (tool) fails     staging discarded at once; live target unchanged      -> FAILED_BEFORE_COMMIT
  validate refuses          staging discarded; live target unchanged              -> FAILED_BEFORE_COMMIT
  process killed in tool    staging left = PREPARED; live unchanged; next write discards it
  aside ok, in fails        rollback renames live back; target unchanged          -> FAILED_BEFORE_COMMIT
  rollback also fails       target ABSENT; retired copy on disk                    -> RECOVERY_REQUIRED
  killed between renames    target ABSENT = TARGET_ABSENT; every reader refuses an absent corpus ("no bodies");
                            the next --recover re-prepares
  renames ok, cleanup fails retired copy left = RETIRED; commit stands; next write discards it
  verify after commit fails target moved, unconfirmed                             -> RECOVERY_REQUIRED
Validation of the staged corpus is the replay's own integrity rule: every body must hash to its observation's
content_sha256, none missing, at least one present.

5 · DECLARED LIMITS — NOT CLAIMED
────────────────────────────────────────────────────────────────
- No power-loss durability: no fsync law exists.
- The replace is two atomic renames, not one: a process killed between them leaves the target ABSENT. That state is
  owned (the next --recover), reported by every reader, and never read as an empty corpus — but it is reachable.
- A failed rollback is not repaired: RECOVERY_REQUIRED is returned and the retired copy is left for the owner.
- The killed-mid-download and failed-rename cases were driven with stand-ins (test/governed-directory-replace.test.mjs
  P-D3 · P-D5 · P-D6 · P-D7), because a real EPERM or a real kill cannot be summoned on demand.
