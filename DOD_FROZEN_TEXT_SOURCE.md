ALMIVISIBILITY
DEFINITION OF DONE
The Frozen Completion Contract for the AlmiWorld Search & AI Visibility Engine
FINAL • 10 SEPTEMBER 2026
1. What AlmiVisibility Must Be When Complete
AlmiVisibility is complete when it functions as one evidence-driven operating system for the AlmiWorld ecosystem: it discovers real search and AI demand, audits technical and content quality, finds opportunities and defects, protects against duplicate/thin inventory, supports high-value programmatic SEO only where justified, monitors real indexation and visibility outcomes, prioritizes actions by value/cost/confidence, produces safe implementation instructions, and verifies what happened after implementation.
It must support SEO, technical SEO, content SEO, pSEO, international/local SEO where applicable, GEO, AEO, AIO/AI visibility, entity/citation intelligence, competitor intelligence, internal-link intelligence, funnel/outcome measurement, and cost governance.
It must prefer owned data, deterministic checks, cached evidence and low-cost methods before paid providers.
It must never promise rankings, indexing, citations, AI recommendations or traffic that have not actually been observed.
It must be safe to operate across AlmiWorld without silently modifying another product or endangering user/product data.
2. Non-Negotiable Historical Failure Controls
UNIVERSE ≠ PAGE COUNT. A keyword/entity/country/city combination is a candidate, not automatically a URL.
QUERY ≠ PAGE. Prefer IMPROVE, MERGE, NOINDEX or REJECT when a new page is not justified.
Batch size is blast-radius control, not a substitute for page quality.
Actual indexing cannot be guaranteed pre-publish. Technical indexability can be checked before publishing; INDEXED status must be learned afterward from search-engine evidence.
Expansion must pause automatically when the prior batch fails its frozen post-publication evidence threshold.
3. Page Creation & Regeneration Laws
NO DUPLICATE PAGE: no candidate may publish if it is duplicate or materially near-duplicate of an existing live page or an approved sibling.
NO THIN PAGE: every generated page must provide substantial, useful, intent-matched value beyond the shared shell/template.
NO BLIND REGENERATION: when the crawler encounters an existing page, the generator must not recreate or overwrite it merely because the URL/query is discovered again.
Existing-page identity must be resolved first using stable URL/entity/query-cluster identifiers plus stored content/version fingerprints.
If the existing page still satisfies the frozen quality and freshness rules, action = KEEP; no regeneration.
If evidence shows the existing page needs work, action must be explicit: IMPROVE, REFRESH, MERGE, REDIRECT, NOINDEX or REJECT. Regeneration is not a default action.
Every content-changing action must preserve provenance/version history so the system can explain what changed, why, from which evidence, and when.
A page generator may create a NEW page only after cannibalization, duplication, thinness, factual-evidence and WHY_THIS_URL_DESERVES_TO_EXIST gates pass.
4. Frozen Pre-Publish Page Quality Gate
A shortfall is a data/content problem. The system must not lower a frozen gate merely to increase page output.
5. Post-Publish Indexation & Learning Gate
Published/submitted/sitemapped does NOT equal indexed.
Track discovery, crawl, canonical selection/indexability signals, actual indexed status where observable, impressions, query coverage and subsequent outcome evidence.
Initial controlled expansion follows 10 → 50 → 200 unless the owner later approves a different evidence-based progression.
The next expansion remains unavailable until the previous batch satisfies the frozen evidence rule.
Repeated failure must produce diagnosis and corrective action, not more page generation.
The system must retain cohort/batch identity so every expansion can be evaluated separately.
5A. Verified Fact Supply Engine — Mandatory Dependency
AlmiVisibility cannot be called complete if its page-quality gates work mechanically but the system has no reliable supply of verified facts. The Fact Supply Engine is a prerequisite for rich-page creation, post-publish indexation learning, and real production recrawl evidence.
If a candidate query has demand but insufficient verified facts to meet the frozen page-quality gate, the correct result is DATA GAP / REJECT — never generic padding or a lowered threshold.
The engine must have enough verified fact supply to create and test a real owner-authorized page cohort. A registry schema with zero usable supply is NOT PASS.
Fact ingestion may use owned data, official/public sources, deterministic extraction and approved research methods, but it must preserve source provenance and respect cost controls.
Source quality must be tiered. High-risk or authoritative claims must use the appropriate authoritative source rather than low-quality secondary repetition.
Where a fact is derived from other verified values, the derivation/formula and input fact IDs must be stored so the result is reproducible.
Stale/expired facts must enter a refresh/reverification workflow. Expired evidence cannot silently continue to satisfy the verified-fact gate.
Conflicting sources must be detected and surfaced for resolution; the system must not silently choose the convenient value.
The system must distinguish verified fact, derived/calculated fact, inference, recommendation, and UNKNOWN.
Facts must be reusable by reference. Page generation must not create independent untraceable copies of the same factual claim.
Every fact must store, as applicable: fact ID, subject/entity, claim/value, unit, locale/scope, source URL or document reference, source tier/authority, extraction date, verified date, freshness/expiry rule, status, and provenance.
Maintain a central VERIFIED FACT REGISTRY that can supply reusable, structured facts to page briefs and other visibility actions.
5A.1 PASS condition for Fact Supply
The owner can inspect where an important page fact came from and when it was last verified.
The supply mechanism can continue acquiring/reverifying facts without requiring manual hand-writing of every record.
Conflict handling, expiry/staleness handling, reuse, provenance, and UNKNOWN behavior are tested.
At least one end-to-end sample proves: authoritative source → verified fact record → page brief/content use → citation/provenance → freshness/reverification path.
A working fact registry exists and is populated with a non-trivial, real verified dataset sufficient to support the first owner-authorized publishing cohort.
5A.2 Dependency law
NO VERIFIED FACT SUPPLY → NO RICH PAGES → NO REAL PUBLISHING COHORT → NO INDEXATION LEARNING → NO REAL RECRAWL PROOF → ALMIVISIBILITY CANNOT BE DONE.
6. Search Demand & Opportunity Intelligence — DONE Criteria
Combines legitimate owned and observable evidence such as Search Console, analytics/site-search where available, SERP/query evidence, competitor gaps, related questions, trends, local-language phrasing and legitimate AI prompt/citation evidence.
Scores rankable/index-worthy QUERY CLUSTERS rather than treating isolated keywords as pages.
Stores intent, locale, demand evidence, competition/difficulty evidence where available, existing AlmiWorld coverage, authority/data strength, business value, freshness and confidence.
Detects whether the correct action is CREATE, IMPROVE, MERGE, NOINDEX, REJECT or MONITOR.
Finds high-opportunity wording for titles/H1/meta/answer-first openings without clickbait, keyword stuffing or unsupported promises.
Uses real performance evidence to learn which wording improves qualified impressions/clicks/conversions.
7. Technical SEO & Crawl Intelligence — DONE Criteria
Audits status codes, redirect chains, canonicals, robots directives, sitemap membership, broken links, orphan risks, rendering/content presence and obvious crawl/indexability conflicts.
Differentiates source-code links from rendered-HTML links where that difference matters.
Finds sitemap URLs that redirect, 404 or are non-indexable.
Maintains page inventory without treating every discovered relationship as a route.
Recrawls/retests changed targets and records PASS/FAIL with evidence rather than merely marking tasks complete.
8. Content, Entity, Internal-Link & Citation Intelligence — DONE Criteria
Detects duplicate, near-duplicate, template-dominated, thin, stale and conflicting content.
Maps important entities/topics/questions to existing coverage and identifies genuine missing evidence or content gaps.
Finds internal-link opportunities and verifies that important links actually appear in rendered HTML.
Tracks factual provenance for important measurable/external-authority claims.
Identifies useful citation/source opportunities and competitor citation gaps without manufacturing citations or spammy link schemes.
Supports refresh/prune/merge decisions so low-value inventory does not accumulate forever.
9. GEO / AEO / AIO / AI Visibility — DONE Criteria
Tracks defined prompts/questions/entities across legitimately measurable AI/search surfaces.
Records dated observations of mentions, citations, cited source domains/pages, competitor presence and answer context where observable.
Separates observation from inference; absence of evidence is not reported as a guaranteed absence everywhere.
Maps AI/search visibility gaps to actionable source/content/entity improvements.
Never fabricates an AI citation, recommendation, ranking or visibility win.
10. Funnel & Business Outcome Intelligence — DONE Criteria
Where product instrumentation exists, connects search/content actions to meaningful downstream outcomes such as qualified visits, signup/trial, product use, paid conversion or other owner-approved goals.
Clearly marks products/events with missing instrumentation as UNKNOWN/NOT MEASURABLE rather than inventing attribution.
Prioritization considers user value, ecosystem/business value, confidence, effort and cost—not traffic volume alone.
11. Cost & Infrastructure — DONE Criteria
Visibility-engine database is isolated from product databases.
Long-running crawling/research work does not depend on an unsuitable request/response hosting path.
FREE / OWNED / DETERMINISTIC / CACHE comes before paid providers wherever technically reasonable.
Paid providers require explicit owner authorization and have budgets/caps/kill switches.
The system records cost per crawl/research/action where measurable and supports cost-per-accepted-action and cost-per-successful-value outcome analysis.
A runaway loop, repeated crawl, repeated generation or uncontrolled queue must have a hard stop.
12. Case Study #1 — Mandatory Proof Before 'DONE'
AlmiVisibility must pass the frozen AlmiOET acceptance test created before implementation. At minimum:
Required result: 6/6 RED defects found independently and 0/3 CONTROL false positives. The acceptance test may not be rewritten after implementation to fit what the engine happens to detect.
13. Operational Reliability & Safety — DONE Criteria
Idempotency: repeating the same crawl/job does not duplicate records, recreate unchanged pages or repeat destructive/paid work.
Deduplication: stable identifiers and fingerprints prevent repeated ingestion/generation of the same logical item.
Retry safety: failed jobs can retry without creating duplicate side effects.
Audit trail: important recommendations/actions show evidence, time, source and status.
Owner control: expensive, destructive, cross-product or large-scale actions remain gated by explicit authorization.
Rollback/recovery exists for implemented changes where applicable.
UNKNOWN is a valid state; the system never converts missing evidence into PASS.
14. Product Experience — DONE Criteria
The interface makes priority, evidence, confidence, cost, status and recommended action understandable to the owner.
The owner can distinguish OBSERVED FACT, INFERENCE, RECOMMENDATION and UNKNOWN.
The owner can see why a page/query/action was accepted, rejected, paused or flagged.
Critical workflows work on desktop and 430px mobile where the product is intended to be used.
Exports/evidence packs are usable for independent review and CC implementation.
15. Completion Ledger — ALL Must Be PASS or Justified N/A
16. What Does NOT Mean DONE
The crawler runs.
The dashboard looks good.
The database has millions of candidates.
Pages were generated.
Pages were submitted in a sitemap.
Pages are technically indexable but actual outcomes were never observed.
A provider/API reports data.
One successful demo works.
The engine detects defects but also flags clean control pages.
The system can create pages but cannot prevent duplicates/thinness/re-generation.
SEO works but GEO/AEO/AIO/citation/outcome/cost layers required by the frozen scope are unfinished.
Claude/CC says 'complete' without the evidence ledger.
The fact-registry mechanism exists but contains no meaningful verified supply capable of supporting a real publishing cohort.
17. FINAL DONE DECLARATION
FACT-SUPPLY COMPLETION RULE: DOD-03A cannot PASS merely because a table/schema or ingestion interface exists. It must demonstrate a real, reusable, provenance-backed verified fact supply sufficient to feed an owner-authorized cohort through the rich-page and post-publish learning loop.
18. Anti-Circle Closure Rule
Once this Definition of Done is frozen, new ideas do not move the finish line. A new issue may block completion only if it is a failure of a frozen requirement, a real regression, new authoritative evidence, a security/data-safety risk, or an owner-approved scope change. Everything else goes to the POST-DONE BACKLOG.
OWNER'S FINISH-LINE RULE
AlmiVisibility is NOT DONE because the dashboard exists, the crawler runs, pages are generated, URLs are submitted, or a phase is deployed. It is DONE only when every applicable requirement in this document is evidenced as PASS or justified N/A, the complete operating loop works on real AlmiWorld products, the historical failure class is controlled, and no frozen Definition-of-Done blocker remains.
CORE LAW
DISCOVER → MEASURE → DECIDE → CREATE/IMPROVE ONLY WHEN JUSTIFIED → PRE-PUBLISH QUALITY GATE → PUBLISH SAFELY → OBSERVE REAL INDEXATION/SEARCH/AI OUTCOMES → LEARN → RE-VERIFY → SCALE. No evidence = no PASS.

The historical failure was not simply 'too many pages'. The failure class was duplicate, thin and non-indexable inventory combined with uncontrolled scale. A large inventory is acceptable only if each URL earns its existence and the system learns from real post-publication evidence.
