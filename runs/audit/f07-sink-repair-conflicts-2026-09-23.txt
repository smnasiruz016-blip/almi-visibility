THE CAUSE
  MIGRATION_CORRELATION = `migration:<governance commit the corpus was migrated from>`. It changes with every corpus
  re-migration. correlationId sits in the content fingerprint but not in the eventId identity, so re-offering an
  already-recorded occurrence gave the same eventId and a different fingerprint, which the store reads as a
  conflicting duplicate. 113 of 113 migrated events carry this shape; 0 native events do.

THE F05 "ASYMMETRY" — EXPLAINED: THERE IS NONE
  F05's events DO conflict: its three board movements (C2 below) and its authority records (inside the 82 A). The
  belief that F05 was unaffected came from the same truncated view: F05's lines were above the 25 that were shown. The
  rule is uniform: a migrated event stored under a pass other than the current one conflicts; one stored under the
  current pass (cd149aea074f) is an IDEMPOTENT retry (10 of them today).

THE FIX (src/audit-trail/event.mjs) AND WHY ONLY C1
  For a MIGRATED event only, correlationId is left out of the content fingerprint: it names the migration pass, not
  the occurrence, and the identity already names the source record. Native events keep correlationId in the
  fingerprint (the parked F08 caution — excluding it globally could merge distinct native events — is respected).
  C2, C3 and C4 are real content differences between the stored record and today's re-draft. Refusing them IS genuine
  conflict detection, and it is kept. No stored event was changed, merged, discarded or relabelled.

  the 8 invalid are exactly C2 (4) + C3 (3) + C4 (1) below; the 93 C1 are now already audited.

PARKED, NOT REPAIRED (content, not identity; each needs a decision, not a fingerprint change)
  C3: a family-B draft records `stateAfter` = the row's state WHEN RECORDED, so every older movement of a row conflicts
      once the row moves again.
  C4: an authority record becoming SUPERSEDED is not recorded as its own event; its original ADMIT event is re-offered

  C2: schema growth of family-B metadata after the first records.
