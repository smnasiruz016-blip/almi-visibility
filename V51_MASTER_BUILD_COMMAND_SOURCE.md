1. Name Decision
Recommended permanent working name: AlmiVisibility. Product descriptor: AlmiWorld Global Search & AI Visibility Engine.
Why this name: it covers Google search, GEO/AEO, AI mentions/citations, local-market discovery, technical SEO and measurement without pretending that any platform's rank is under our control.
Internal shorthand: AVE (AlmiVisibility Engine).
Repository suggestion: almi-visibility.
Do not use 'AlmiSEO' as the main name because the system is materially broader than SEO.
Do not use a name that promises #1 rankings or guaranteed AI placement.
2. Non-Negotiable Mission
AlmiVisibility must continuously answer one operational question: "For each AlmiWorld product and each relevant global user journey, what are people actually searching/asking, what useful verified answer can AlmiWorld provide, what prevents discovery/citation today, what should be fixed or created next, and did the change measurably improve visibility?"
Core operating loop:
DISCOVER → UNDERSTAND → MAP → SCORE → CREATE/IMPROVE/MERGE/REJECT → QA → PUBLISH → CRAWL/INDEX VERIFY → MEASURE → AI VISIBILITY TEST → LEARN → PRIORITIZE → GENERATE CC COMMAND → RETEST
3. Owner Vision Converted into System Rules
AlmiWorld is global by design: all 197 countries belong in the underlying model.
Origin and destination are first-class dimensions whenever the user journey depends on movement between countries.
Do not translate one English keyword 197 times and call that localization. Discover how people in each market naturally search, including local languages, English, mixed-language behaviour, local terminology and cultural phrasing.
Answer the user's real wording and intent naturally. Do not keyword-stuff.
Large mathematical universes are allowed. Universe size is NOT page count.
A dedicated public/indexable URL exists only when it has a defensible reason to exist: distinct intent, sufficient real data, useful answer, appropriate localization, verified facts where required, and low duplication/thin-content risk.
Free products are strategic discovery doors, not secondary products.
Every page should connect to the logical next AlmiWorld step where useful to the user, not merely to manufacture internal links.
The system must work product-by-product and must respect AlmiWorld's one-product-at-a-time completion workflow.
4. Global Intent Graph
Canonical conceptual model:
PERSONA × ORIGIN × DESTINATION × GOAL × ENTITY × REQUIREMENT × LANGUAGE/LOCALE × NATURAL QUERY × INTENT × ALMIWORLD DATA × SOURCE PROVENANCE × NEXT ACTION
Not every dimension applies to every product. The engine must use product-specific schemas rather than force every product into one universal multiplication.

6. Local Search Intelligence Engine
This is a core differentiator, not an optional feature.
Choose product, origin, destination, persona/entity and goal.
Discover real query evidence from available legitimate sources: Search Console, search suggestions/related questions where permitted, trend data, public SERPs, official sources, competitor coverage, community phrasing, and existing AlmiWorld search/referral data.
Detect likely search languages/locales for the market. Country and language must never be treated as synonyms.

Map each cluster to existing AlmiWorld content/data.
Identify: covered well / covered weakly / missing / cannot safely answer / requires verification.
Recommend the best content action rather than automatically creating a URL.
Example:
Pakistan → Doctor → UK → Work
Possible discovered intents: eligibility, registration, English test, OET/IELTS, salary, CV, job sources.
The engine must discover actual wording before recommending content; these labels are conceptual examples, not assumed keywords.
7. Page Opportunity & Indexability Decision Engine
Required outputs: CREATE | IMPROVE | MERGE | NOINDEX | REJECT
Every candidate must store an explicit field: WHY_THIS_URL_DESERVES_TO_EXIST.
Real user/search intent evidence.
Materially distinct answer from existing URLs.
Sufficient first-party/verified AlmiWorld data.
Ability to satisfy the query, not merely mention its keywords.
Verified/current facts where high-trust or measurable claims are involved.
Unique local/corridor value where origin/destination is used.
No doorway-page pattern.
No near-duplicate translation or country-name swapping with little added value.
Clear canonical strategy.
Crawlable, useful main content in rendered HTML.
Logical place in information architecture and internal-link graph.
Clear next user action.
Suggested transparent scoring model (weights must be configurable and calibrated on real outcomes):
OpportunityScore = DemandEvidence + IntentFit + DataStrength + DistinctValue + LocalRelevance + EcosystemValue + SourceConfidence - DuplicationRisk - ThinContentRisk - ComplianceRisk
Never let a numeric score override a hard safety/quality gate. A high score cannot publish unverifiable, misleading, copied, doorway or thin content.

31. Historical Cost Failure - Mandatory Design Constraint
The owner previously experienced a large-scale deployment involving approximately 43 million generated pages. The deployment produced duplicate, thin and non-indexable pages and caused Vercel spend reported by the owner at more than approximately USD 100-150 per week. The owner stopped that system because the cost was not affordable and the generated inventory was not providing justified value.
This is not a footnote. AlmiVisibility must be architected specifically so that this class of failure cannot recur accidentally.
A mathematical combination is never permission to create a physical URL.
A research record is never permission to render/build a page.
A generated draft is never permission to deploy.
A deployed page is never automatically permission to add it to a sitemap.
A sitemap entry is never a claim that Google or any AI system will index, rank or cite it.
Discovery, page generation, deployment, sitemap submission and index monitoring are separate permissioned stages.
Default state for new page candidates is NOT PUBLISHED.
32. Cost & Mass-Page Disaster Prevention Gate
This is a HARD GATE and must be implemented before any page-generation feature is enabled.
Global kill switch: instantly pause research jobs, AI jobs, crawls, page generation and deployment queues independently.
Per-product kill switches.
Hard maximum candidate-generation batch size.
Hard maximum deployable-page batch size; configurable by owner. Start conservatively.
No 'generate all combinations' or 'publish all' action in the UI.
Owner approval required for any batch above the configured safe threshold.
Pre-deploy duplicate and near-duplicate detection.
Pre-deploy thin-content and unique-value checks.
Pre-deploy indexability/canonical/robots checks.
Pre-deploy route/build cardinality estimate: estimate how many routes/build artifacts/ISR entries/database rows/jobs/sitemap entries the change can create.
Pre-deploy infrastructure-cost estimate where reasonably measurable.
Post-deploy cost anomaly monitoring and alerting.
Sitemap admission gate: only approved canonical URLs intended for indexing can enter XML sitemaps.
Rollback/disable plan for every page-generation batch.
Automatic pause if cost, error rate, generated URL count or queue size crosses owner-configured thresholds.
Required invariant:
POTENTIAL_RELATIONSHIPS can be millions. PHYSICAL_PUBLIC_URLS must remain only the evidence-backed, approved subset.
33. Cost Ledger & Budget Governor
AlmiVisibility must make cost visible before it makes intelligence impressive. Every external paid operation must be attributable to a product/job/provider.
No paid provider is enabled by default merely because an integration exists.
Every job should record estimated cost before execution when possible and actual cost/usage afterward.
Dashboard: today, 7 days, month-to-date, by product, by provider, by job type.
Owner-configurable warning threshold and hard-stop threshold.
If exact provider cost is unavailable in real time, track tokens/requests/runtime/builds and clearly label monetary estimates as estimates.

46. Multi-Provider Agent Architecture — LOCKED
AlmiVisibility must not be architecturally dependent on Claude alone. Build a provider-neutral research/orchestration layer so approved Claude, OpenAI/GPT, Gemini, and future providers can be added, removed, paused or replaced without rewriting the core visibility engine.
Required routing principle:
CODE/RULES → VERIFIED CACHE → OWNED DATA → CHEAPEST RELIABLE APPROVED PROVIDER → SECOND PROVIDER ONLY WHEN JUSTIFIED → HUMAN/OWNER REVIEW FOR HIGH-RISK CONFLICT
47. Provider Router — No Triple Billing by Default
Do NOT automatically ask Claude, GPT and Gemini the same question. Multi-provider capability exists to reduce dependency and improve cost/quality, not to multiply spend.
Each research job receives a task type, risk level, freshness need, expected value, maximum spend and required evidence quality.
Router checks verified cache and owned data before any paid AI call.
Router chooses one primary provider using measured cost, historical task quality, source quality, latency and availability.
A second provider is called only for configured reasons: high-stakes fact, conflicting evidence, low confidence, failed quality gate, provider outage, or explicit owner/reviewer request.
Three-provider consensus/jury mode is exceptional and disabled by default.
Provider choice and fallback reason must be logged for auditability.
48. Provider Performance & Cost Scorecard
AlmiVisibility should learn from its own workload instead of assuming one model is always best.
The router may develop task-specific preferences only from measured evidence. Example: Gemini may be preferred for a Google-grounded local-market research task if it passes quality at lower total cost; Claude may be preferred for complex synthesis; GPT may be preferred for another research/classification task. These are examples, not hard-coded assumptions.
49. Multi-Agent Research Patterns
Single-agent default: one focused provider researches a clearly bounded task.
Specialist split: independent sub-tasks may be assigned to different agents only when parallelism saves time/cost or improves evidence quality.
Verifier pattern: primary agent researches; a cheaper deterministic verifier or second provider checks only uncertain/high-risk outputs.
Escalation pattern: cheap model first; retry only failed/ambiguous cases at stronger intelligence.
Jury pattern: Claude + GPT + Gemini compare conclusions/sources only for rare high-value/high-trust conflicts.
